# FRD: post-management

## Summary
Реализация фичи публикаций (posts) для конечных пользователей мессенджера. Пользователь может создавать текстовые посты с медиа-вложениями (до 5 файлов), просматривать, редактировать текст, мягко удалять и просматривать ленту постов конкретного пользователя. Архитектурно зеркалит существующую фичу `user` в рамках feature-first hexagonal подхода.

## Problem & Intent
Конечный пользователь мессенджера хочет публиковать контент (текст, фото, видео), чтобы делиться им со своей аудиторией. Успех = пост опубликован, медиа загружено и доступно, пост виден другим пользователям в профиле автора. Сейчас в проекте нет никакого кода, связанного с публикациями.

## Goals
- Пользователь может создать пост с текстом (до 5000 символов) и прикрепить до 5 медиафайлов
- Пользователь может просмотреть свой пост и посты других пользователей по ID
- Пользователь может просматривать ленту всех постов конкретного пользователя
- Пользователь может редактировать текст существующего поста
- Пользователь может мягко удалить свой пост (скрыть из выдачи, сохранить в БД)
- Медиафайлы загружаются через отдельный эндпоинт перед созданием поста

## Non-Goals
- Черновики (drafts) — отложены на следующую итерацию
- Лимиты публикаций (rate limiting) — отложены
- Глобальная лента / лента подписок — требует фичи подписок
- Редактирование медиа-вложений при обновлении поста
- Уведомления подписчикам о новых постах
- Модерация контента (AI или ручная)

## Functional Requirements
1. **FR1** Система позволяет аутентифицированному пользователю создать пост: `POST /api/v1/posts` с текстом и списком URL загруженных медиафайлов.
2. **FR2** Система позволяет получить пост по ID: `GET /api/v1/posts/{id}`. Если пост мягко удалён — возвращает 404.
3. **FR3** Система позволяет получить список постов конкретного пользователя с пагинацией: `GET /api/v1/users/{userId}/posts?page=&size=`.
4. **FR4** Система позволяет автору отредактировать текст поста: `PUT /api/v1/posts/{id}`. Медиа при этом не изменяется.
5. **FR5** Система позволяет автору мягко удалить пост: `DELETE /api/v1/posts/{id}`. Пост помечается `deleted=true` и скрывается из выдачи.
6. **FR6** Система позволяет загрузить медиафайлы отдельным запросом: `POST /api/v1/posts/media` (multipart/form-data, до 5 файлов, JPEG/PNG/GIF/MP4/WEBM, до 50MB каждый).
7. **FR7** Система валидирует текст поста: `@Size(max = 5000)`, `@NotBlank`.
8. **FR8** Система денормализует данные автора в сущности Post (`authorId`, `authorName`, `authorAvatarUrl`) — snapshot на момент публикации.

## Non-Functional Requirements
- **Performance**: Пагинация по умолчанию `page=0, size=20`, макс `size=100`. Время ответа < 200ms для GET запросов при размере таблицы < 1M записей.
- **Security**: Все эндпоинты требуют аутентификации (кроме просмотра постов — если решено позже). Авторизация: только автор может редактировать/удалять свой пост. Проверка через `Principal` (userId из токена).
- **UX / Accessibility**: Сообщения валидации и ошибок на русском языке (как в существующем проекте).
- **Reliability**: Мягкое удаление гарантирует, что пост не пропадёт безвозвратно. Транзакционная загрузка медиа: если БД-операция откатывается, загруженные файлы удаляются (rollback cleanup через `TransactionSynchronizationManager`).

## Constraints & Assumptions
- Технологический стек: Gradle, Spring Boot 4.0.6, Java 25, PostgreSQL, Flyway, JPA, MapStruct, Lombok, SpringDoc OpenAPI
- Архитектура: feature-first hexagonal (ports & adapters). Каждая фича — изолированный пакет `feature/post/*` с подпакетами `api/`, `controller/`, `service/`, `entity/`, `repository/`, `presentation/`, `infrastructure/`
- Cross-feature зависимости только через порты в `api/` — никаких импортов `service/`, `entity/`, `repository/` из других фич
- БД-схема управляется через Flyway миграции. `spring.jpa.hibernate.ddl-auto=validate` — ручное создание таблиц через SQL
- Каждая фича имеет свою реализацию хранилища медиафайлов (адаптер в `infrastructure/`), даже если интерфейс порта (`MediaStoragePort`) импортируется из другой фичи
- Данные автора (имя, аватар) хранятся в `Post` как денормализованный snapshot — не требует runtime-запросов к `feature/user`

## Acceptance Criteria
- [ ] Запуск `./gradlew test` проходит без ошибок; новые тесты для `PostService`, `PostController`, `PostRepository` включены
- [ ] `POST /api/v1/posts` с JSON `{ "content": "...", "mediaUrls": [...] }` возвращает `201 Created` и `PostDTO`
- [ ] `GET /api/v1/posts/{id}` возвращает пост с денормализованными данными автора; удалённый пост возвращает `404`
- [ ] `GET /api/v1/users/{userId}/posts?page=0&size=10` возвращает пагинированный список `PostDTO`, отсортированный по `createdAt` DESC
- [ ] `PUT /api/v1/posts/{id}` обновляет только текст; попытка изменить медиа игнорируется
- [ ] `DELETE /api/v1/posts/{id}` от автора возвращает `204 No Content`; последующий GET возвращает `404`
- [ ] `POST /api/v1/posts/media` с multipart принимает до 5 файлов, возвращает список URL; файлы >50MB или неподдерживаемого формата отклоняются с `400`
- [ ] Попытка редактировать/удалить чужой пост возвращает `403 Access Denied`
- [ ] `UserService` и `AuthService` не импортируют ничего из `feature/post/service/`, `entity/` или `repository/`
- [ ] Flyway-миграция `V4__create_posts_and_post_media.sql` создаёт таблицы без ошибок при старте приложения

## Recommended Approach
Новая фича `feature/post/` зеркалит структуру `feature/user/`: порты `PostQueryPort`/`PostCommandPort` в `api/`, package-private `PostService` реализует порты, `PostController` на `/api/v1/posts` зависит только от портов, JPA-сущности `Post` и `PostMedia` с `@PrePersist` и `@Version`, репозитории на `JpaRepository`, DTO как `record` с `@Schema`, MapStruct-маппер. Загрузка медиа через отдельный адаптер `feature/post/infrastructure/LocalPostMediaStorageAdapter`, реализующий `MediaStoragePort` из `feature/user/api/`. Cross-feature интеграция с `user` — через `UserQueryPort` (только для проверки существования автора при создании, если потребуется). Flyway-миграция `V4__create_posts_and_post_media.sql`.

**Recommended**: Post будет использовать `UserQueryPort` / `UserProvisioningPort` из `feature/user/api/` для проверки автора и прав

**Rationale**: `evidence: src/main/java/lghdnov/msocial/feature/auth/service/AuthService.java:34` + confirmed. `auth` уже потребляет `UserProvisioningPort` из `user/api/`.

### Медиа-хранение

**Recommended**: Переиспользовать существующий `MediaStoragePort` из `feature/user/api/` для прикреплённых файлов
**Chosen**: Интерфейс `MediaStoragePort` импортируется из `feature/user/api/`, но реализация адаптера (`LocalPostMediaStorageAdapter`) живёт в `feature/post/infrastructure/`
**Rationale**: `evidence: src/main/java/lghdnov/msocial/feature/user/api/MediaStoragePort.java:13` + confirmed с коррекцией «у каждой фичи своя реализация хранилища»

### БД-миграции
**Question**: Pre-resolved from codebase evidence — confirmed in Step 4
**Recommended**: Создать таблицы через Flyway миграцию `V4__create_posts_and_post_media.sql`
**Chosen**: БД через Flyway миграцию
**Rationale**: `evidence: src/main/resources/application.yaml:16-19` + confirmed. Проект использует Flyway с `ddl-auto=validate`.

### Scope первой итерации
**Question**: Какие операции с постами входят в первую итерацию (MVP)?
**Recommended**: CRUD + лента (без черновиков и лимитов)
**Chosen**: CRUD + лента постов конкретного пользователя
**Rationale**: Быстрый MVP с максимальной ценностью для пользователя. Черновики и rate limit — отложены.

### Медиа-вложения
**Question**: Какие медиа-вложения поддерживает пост в первой итерации?
**Recommended**: Текст + до 5 медиафайлов
**Chosen**: Текст + до 5 медиафайлов (JPEG, PNG, GIF, MP4, WEBM до 50MB), загрузка через отдельный эндпоинт
**Rationale**: Соответствует UC3 из спецификации, но упрощено (без галереи до 10 файлов).

### Лента постов
**Question**: Что подразумевается под «лентой постов» в первой итерации?
**Recommended**: Оба варианта (посты по автору + глобальная лента)
**Chosen**: Посты конкретного пользователя (GET /api/v1/users/{userId}/posts)
**Rationale**: Глобальная лента требует фичи подписок или публичной выдачи, которая вне текущего scope.

### Данные автора в посте
**Question**: Как `post` получает данные автора при отображении поста?
**Recommended**: Post сам хранит копию (snapshot)
**Chosen**: Денормализованный snapshot: `authorId`, `authorName`, `authorAvatarUrl` в сущности `Post`
**Rationale**: Оптимизирует чтение, избегает cross-feature вызовов при каждом GET. Данные профиля меняются редко.

### Редактирование медиа
**Question**: Что происходит с медиа при редактировании поста?
**Recommended**: Только текст
**Chosen**: Редактирование только текста; медиа неизменяемы
**Rationale**: Упрощает реализацию и валидацию жизненного цикла файлов. Для смены медиа — удалить и создать новый пост.

### Удаление поста
**Question**: Как реализовать удаление поста?
**Recommended**: Мягкое удаление
**Chosen**: Мягкое удаление (`deleted = true`), пост скрывается из выдачи
**Rationale**: Соответствует паттерну в спецификации UC3, позволяет восстановить пост и сохраняет целостность связанных данных (комментарии в будущем).

### Ограничение текста
**Question**: Какие ограничения на текст поста?
**Recommended**: Макс 2000 символов
**Chosen**: Макс 5000 символов
**Rationale**: Пользователь предпочёл более свободный формат, как в блог-платформах.

### Ограничения на медиафайлы
**Question**: Какие ограничения на загружаемые медиафайлы?
**Recommended**: Картинки + видео до 50MB
**Chosen**: Картинки + видео до 50MB, до 5 файлов на пост
**Rationale**: Соответствует UC3, баланс между функциональностью и безопасностью.
